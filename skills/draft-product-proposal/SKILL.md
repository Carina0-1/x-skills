# 产品方案初稿

把分散的想法整理成一份能支持方向讨论、范围取舍和下一步验证的初稿。读者应能判断：服务谁、解决什么问题、为什么值得做、首版做什么、怎样验证，以及哪些问题仍待确认。

## 1. 获取上下文并确定本稿用途

优先使用当前对话、用户指定的材料和已有方案，提取以下信息：

- 产品对象、所处阶段、本次文档用途和主要读者。
- 目标用户、实际使用者，以及影响购买、推广或验收的角色。
- 想解决的任务与问题、用户目前的替代做法。
- 已有系统、数据、团队、Demo 等基础，以及明确的约束。
- 用户已经确定的优先级、范围取舍和最新修正。

用户已经回答过的问题不要重问。更新已有方案时，以最新明确要求替换过时结论，不把历史讨论中的每个想法都累积进范围。

信息不足时按影响处理：

| 缺失情况 | 处理方式 |
| --- | --- |
| 不影响主体方向，如预算、确切工期尚未确定 | 继续写，列为待确认项；需要暂定值时标明“建议”及依据 |
| 会改变方案方向，如产品服务对象存在互斥理解 | 尽早提出少量针对性问题，同时整理不依赖答案的内容；若仍需先交稿，明确本稿采用的假设及适用范围 |
| 用户只有零散想法 | 提出合理的初稿假设并完成文档，不要求先做完访谈、交齐材料或批准目录 |
| 用户已指定模板、篇幅或章节 | 优先遵循，补足关键判断，合并重复内容 |

除非用户要求开展研究，资料调研不应成为写初稿的前置门槛。需要引用外部市场、政策、标准、竞品或价格等事实时，使用适当检索工具核实并附支持该结论的来源；无法核实时改为待验证问题，不编造依据。

## 2. 建立方案的判断链

写作前明确：**用户在什么情境下完成什么任务 → 现有做法哪里受阻 → 产品提供什么改善 → 哪些能力支持改善 → 什么证据能证明改善。**

遇到只有功能清单的输入，先把功能归到具体任务。找不到任务或价值依据的功能，列为候选或后续范围，并说明进入条件。

根据本稿用途确定阶段目标：探索方向看问题与价值是否成立，Demo 看任务流程是否可用，试点看真实使用效果，正式交付看实施与验收条件。一个稿件可以涉及多个阶段，但首版应有明确的主目标。

## 3. 写出可独立阅读的完整初稿

阅读 [核心内容与写作框架](references/proposal-framework.md)，按产品阶段组织内容。默认覆盖以下八项，可调整顺序、合并章节：

1. 背景、已知条件与问题假设。
2. 目标用户、决策角色与产品定位。
3. 产品价值、替代方案与差异化假设。
4. 核心场景及完整任务流程。
5. 首版范围、优先级与后续范围。
6. 核心对象、关系与关键业务规则。
7. 验证计划、评价指标与决策条件。
8. 推进阶段、依赖、风险和待确认事项。

开头用简短概述交代定位、阶段目标和首版重点。版本、日期、用途等元信息按需添加。最终文档直接进入主题，不放“下面这版”“根据我们的讨论”等对话前言，不保留未填写的模板占位符。

按决策需要分配篇幅。概念探索可以轻写业务规则，已有复杂产品则需要写清对象与规则；不要为了凑章节重复内容，也不要把首稿膨胀成逐页面、逐字段的实现规格。

## 4. 控制事实、范围与指标的质量

### 事实与假设

- 用户提供的现状注明来源；未经核实的实现状态按“用户描述”或“待核查”表达。
- 问题假设、价值主张和差异化主张分别说明需要什么证据，不能把设想写成已验证结论。
- 不编造访谈、市场规模、采购预算、竞争优势、上线状态或效果提升数值。
- 区分当前已实现、Demo 模拟、首版计划和远期方向。需要核实本地实现时，只检查与结论相关的材料；写方案本身不要求开展代码审计。
- 区分系统产出和真实结果。例如生成报告不等于业务改善，发布成果不等于通过验收，相关性不等于因果关系。

### 范围与规则

- 围绕一个明确的首版目标形成能完成任务的流程，覆盖必要输入、主操作、结果及主要异常处理。
- P0 表示完成首版任务必需的能力；P1 表示重要但可以通过替代方式完成的能力；后续能力说明进入条件。用户已有优先级体系时沿用。
- 对每项首版能力写清对应任务、价值及验证方式。基础依赖和主要例外也要进入范围判断。
- 把用户这次产品的特殊约束写入该产品方案，不默认推广成所有产品都必须遵守的规则。
- 有 AI 参与时写清输入依据、输出性质、人工判断节点、失败处理和质量评价方式。若评审本身有成本，计入核验与返工投入；模型自评不能直接替代独立质量检查。

### 验证与指标

- 优先选择能反映任务完成、时间或成本、产出质量、真实采用的指标；节点数、点击量等规模指标只能解释背景，不能单独证明价值。
- 每个关键指标说明定义、统计单位或分母、数据来源、测量时点及比较方式。数据暂不可得时给出采集方案。
- 将效率与质量一起评价，避免通过缩小范围或省略核验得到“提升”。成本包含人工、核验、返工及相关系统投入。
- 没有基线时，建议先采集基线；数值目标属于暂定目标，说明依据，不能声称是行业标准。
- 验证计划须包含真实任务、参与角色、观察或数据记录、完成标准，以及支持继续、调整或暂停投入的证据。人数、周期和阈值根据风险与资源提出建议，不机械固定。

## 5. 交付前检查

逐项检查，直接修订发现的问题，不额外输出一份冗长自评：

- 读者是否能看出本稿要支持什么决定，以及首版主要服务谁？
- 核心问题、价值、场景、范围和指标是否相互对应？
- 事实、推测和方案建议是否容易区分，是否存在未经支持的肯定结论？
- 首版是否能完成主要任务，重要依赖和异常是否遗漏？
- 对象、关系和术语是否一致，规则之间是否冲突？
- 验证是否能发现失败原因，决策条件是否可执行？
- 待确认项是否说明影响、确认方式或负责角色，是否避免阻塞无关工作？
- 文档是否摆脱对聊天记录的依赖，是否去掉重复、口号及空泛表述？

## 6. 保存与交付

用户只要求生成方案而未指定格式时，默认生成 Markdown 文件。优先使用指定路径；否则保存到当前工作目录，文件名采用 `产品名称-产品方案初稿.md`，名称未知时采用 `产品方案初稿.md`。版本号和日期使用实际信息。

修改已指定的方案时在原文件更新；生成独立新方案时避免覆盖不同产品的已有文件。具备写入工具就实际保存，检查文件存在、内容完整、引用有效且无占位符，并在适合时打开预览。若当前环境无法保存，交付完整正文并明确未写入文件。

最终回复简短说明保存位置、包含的重点和必要的未决问题，提供可点击的文件链接。已保存的全文无需再次粘贴到聊天。用户要求其他格式时使用相应能力完成；文档交付不自动扩展为开发 Demo、发布网站或对外发送。
