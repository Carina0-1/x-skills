# 终版 PRD 格式规范

这份规范是从原教育平台项目的 `local.docs/AI PRD/PRD 题库管理.md` 和 `local.docs/AI PRD/PRD 作业与练习.md`
两份已经过人工审核定稿的终版文档里反推出来的。此处提及的原文档仅说明规范来源，不是使用本技能所需的外部依赖。
它们的初版（`PRD-初版-*.md`）在结构上是对的，
但在"读者体验"上不够克制——终版做的事情，本质上都是把"写给自己看的分析过程"改成"写给协作者看的结论"。
生成 PRD 时直接按这份规范的结构走，不要重新发明格式。

## 整体结构

标题只用一行 `# PRD {模块名}`，模块名与用户草稿标题保持一致的简称（如"题库管理"而非"题库管理（教师端）"）。
**不要**在标题下加"状态：草稿 v1.0""关联文档：……"这类元信息头——这些是写作过程中的脚手架，
终版是交付物，读者不需要知道它经历了几轮草稿。如果确实需要注明引用了哪些其他模块的 PRD，
把引用写在提到该模块的正文句子里（例如"沿用 `PRD-题库管理` 定义"），不要单独开一个头部区块。

标准章节顺序（不是每份都必须全部出现，但出现时保持这个顺序）：

1. 背景与目标
2. 术语与核心实体（含实体关系图）
3. 权限与角色说明
4. 核心实体字段表（如果模块有多个子概念，如"单元练习"和"主观作业"，各开一个大节，字段表是其下小节）
5. 页面与交互流程
6. 异常与边界情况（可选，一般并入各页面描述里的边界说明，只有横跨多个页面的通用异常才单独成节）
7. 与其他模块的关系
8. 版本记录（放最后一节，不用"---"分隔线单独强调）

## 各章节的写法

### 背景与目标
一段话说清楚"这个模块是什么、解决什么问题、和相邻模块的边界在哪"。用加粗小标题列 **目标**、
**本期范围**、**本期不做** 三块，各用无序列表列 2-4 条，不要展开论证，一句话一条。

### 术语与核心实体
表格两列：术语、说明。说明控制在一句话内。然后是一段 ` ```plaintext ` 代码块画实体关系，
用 `1 ── N` `N ── N` 这种简单符号，不需要 ER 图工具语法。图后面补一段话说明关键的解耦关系
（例如"题库与课程是解耦的"），这段话往往是全文档最重要的一句话，因为它决定了后面字段表怎么设计。

### 权限与角色说明
按角色分点：谁能看/改什么范围的数据。"本期不做"的权限扩展方向单独一段，
说明"为什么不做"（通常是"避免过早引入复杂模型，等真实需求出现再设计"这类判断），
而不是简单罗列"以后可能要做 X、Y、Z"。

### 核心实体字段表
表格四列：字段名、类型、必填、说明。**这是终版和初版差异最大的地方**：
初版里"说明"列经常塞进 `*` 开头的多条子列表（用 Markdown 的多行 bullet 挤在一个单元格里），
终版一律收成一段连贯的话，用中文顿号或句号分隔要点，不再用嵌套 bullet。
例如初版的：
```
| 选项 | ... | *   至少 2 个选项<br>*   可增删<br>*   上限10个 |
```
终版写成：
```
| 选项 | ... | 至少 2 个选项，可增删，上限 10 个 |
```
如果一个字段本期不做，整行用删除线（`~~字段名~~`）标注，而不是单独放一个"本期不做"小表格——
除非"本期不做"的字段有 3 个以上，那时候可以单独分表格更清楚，参考"提交方式配置"和"使用统计字段"两种不同处理方式的取舍：字段少（1-2个）用删除线内嵌，字段多且成体系用独立小节。

有"现状说明"这一类框（引用块 `>` 开头，写"原型中如何如何，正式产品应该如何如何"）的，
**终版一律删除**，把"正式产品应该如何"的结论直接写进校验规则或说明列，不保留"原型现状"这半句。
终版读者是要拿着这份文档去对接开发的人，不需要知道"这是相对原型的哪个差距"。

### 页面与交互流程
每个页面一个小节（`#### 教师端 · xxx页`），内部顺序：核心展示字段 → 筛选/检索/排序 →
行内操作与流程。用加粗小标题起头 + 无序列表，不要写成大段叙事段落。
状态类字段（如"状态：未发布/进行中/已截止"）要把全部枚举值列出来，并说明每个状态下页面/按钮的具体表现
（例如"已截止：按钮置灰，不可进入答题页"），这是初版经常遗漏、需要靠追问补齐的细节。
空态、默认排序、默认筛选值这类"看起来很小但决定体验"的点，能确定的都要写出来，
不确定的使用当前环境可用的提问方式向用户确认（见 SKILL.md 正文）。

### 与其他模块的关系
只写"依赖什么、被谁依赖、通过什么字段/机制关联"，一模块一小节。
如果关系已经在其他模块的终版 PRD 里权威定义过（例如题库的"快照机制"），
这里只引用结论（"遵循 `PRD-题库管理`，本文档不重复展开"），不要复制黏贴原文。

### 版本记录
表格四列：版本、日期、修改人、修改内容。终版只保留一行 `v1.0`，"修改内容"写"完成初版产品设计"
这类简短总结，不要像初版那样写一整句"基于原型现状盘点与产品决策，正式成文；补全 XX、YY、ZZ 等章节"——
那是写给自己看的工作记录，终版读者不关心。**修改人一栏必须是真实姓名，不能留"—"或"AI生成"**，
生成前向用户确认这次的修改人姓名（通常沿用上一份终版 PRD 里的名字，除非用户说换人了）。

## 语言与排版细节

- 优先用清晰的 `-` 无序列表，避免初版里常见的"每条 bullet 之间空一行"的松散排版（Markdown 渲染会拉开间距，让本该紧凑的列表显得很长）。
- 加粗只用在真正的关键词/小标题上（如 **目标**、**本期不做**），不要整句加粗。
- 表格优先于大段文字：任何"字段 + 说明"结构的内容都应该表格化，不要写成"XX字段用于表示……，YY字段表示……"的连续段落。
- 不用"疑问""待确认"这类字眼留在正文里——正文只写结论；真正待确认的问题在生成过程中当场问用户，不留到文档里让读者去猜。
