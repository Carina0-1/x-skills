# PRD 生成器

把一份"提纲式"的手写草稿 PRD，结合目标项目原型代码里的真实实现细节，写成一份可以交付给研发的终版 PRD。
默认产出到目标项目的 `local.docs/AI PRD/PRD {模块名}.md`；用户指定输出路径时遵循用户要求。
不额外生成中间的“初版”文件。

这份技能是从两次真实的人工审核（题库管理、作业与练习两个模块）里反推出来的：人工审核花的功夫，
绝大部分不是"改错别字"，而是三类工作——(1) 把结构上啰嗦的表格/列表收紧，(2) 补齐原型代码里
体现不出来、需要产品经验判断的交互细节，(3) 对"草稿和代码都没写清楚该怎么办"的地方做出取舍。
下面的流程就是把这三类工作往前搬，尽量在生成阶段就做完，而不是留给人工审核阶段。

## 输入

先确定目标项目根目录、草稿路径、原型位置和输出路径。用户提供的路径优先；否则从当前业务项目定位。
以下 `local.docs/`、`pages/`、`assets/js/` 是原教育平台项目的默认约定，均相对于目标项目根目录，
不是相对于本 skill 的安装目录。其他项目按实际目录结构查找，不能因默认目录不存在就认定缺少输入。
如果当前目录只是 skills 管理仓库，且用户没有指定业务项目或输入文件，先询问目标项目位置。

1. **草稿 PRD**：通常在 `local.docs/手写文档/PRD-草稿 - {模块名}.md` 或类似路径，内容是提纲式的——
   功能目标、核心实体、字段罗列、页面清单、简单的交互流程，往往不完整、不成段落。
   如果用户没有直接给路径，先用 `rg --files` 在目标项目的文档目录查找；有多个候选时再向用户确认是哪一份。

2. **原型代码**：草稿里提到的页面对应到 `pages/teacher/` 或 `pages/student/` 下的 html 文件，
   以及它们依赖的 `assets/js/*.js`。在原教育平台项目中，教师端页面文件名以 `teacher-` 开头；
   其他项目按实际路由、组件和脚本结构定位，不要求相同的文件名或技术栈。
   直接读这些代码文件——不需要用浏览器实际操作原型，字段、校验规则、mock 数据、状态流转这些
   在代码里都能读到，读代码更快也更完整（能看到浏览器操作不会触发的分支逻辑）。

3. **已有的其他模块终版 PRD**（`local.docs/AI PRD/PRD *.md`，排除待生成的这一份）：
   如果新模块依赖或关联已经成文的模块（比如"作业与练习"依赖"题库管理"的组卷/快照机制），
   要引用已有 PRD 的结论，不要重新定义一遍。生成前扫一眼这个目录里已有哪些文件。

## 工作流程

### 第 1 步：读草稿，列出要覆盖的范围

读草稿 PRD，提炼出：功能目标、核心实体清单、涉及的页面列表、草稿里已经给出的字段和规则。
草稿是"范围骨架"——它规定了这份 PRD 要覆盖哪些实体、哪些页面，后续所有分析都不应该超出或遗漏这个范围
（除非原型代码里明显有草稿没提到但属于同一模块的页面/字段，这种情况要提醒用户是否要一并纳入，而不是自作主张扩大范围）。

### 第 2 步：定位并通读原型代码

根据草稿里提到的页面名/功能点，找到对应的 html 和 js 文件。逐个通读，重点关注：

- **字段的真实约束**：代码里的表单校验逻辑，哪些字段实际必填、哪些只是摆设（比如原型可能只做了非空校验，
  没做格式/范围校验）——这类"原型简化 vs 应有约束"的差异，终版要写"应有的约束"，不要照抄原型的松散校验。
- **状态与流转**：列表页的状态筛选项、状态对应的按钮文案和可用性（例如"已截止"状态下按钮是否置灰）、
  数据写入的 key（sessionStorage/内存变量名），这些决定了字段表和交互流程该怎么写。
  项目里存在 mock 数据跨页面持久化的限制（sessionStorage vs 内存数组），如果代码里能看出某个数据
  用了哪种存储方式，这个事实本身通常不需要写进 PRD（PRD 描述的是产品行为，不是实现细节），
  但如果代码注释或数据结构明确暴露了"这是简化 mock、正式产品要联动真实数据"这类信息，
  要把"应有的真实行为"写进正文，不要把"mock 现状"写进正文。
- **交互细节**：默认排序、默认筛选值、空态提示文案、弹窗的二次确认时机、批量操作的成功/失败反馈方式。
  这些在代码里往往就是几行 JS（比如数组的 `.sort()` 参数、条件渲染里的空态分支），扫一遍能读到，
  不需要靠人工点开原型体验才能发现——认真读代码就能补齐初版里遗漏的这类细节。

如果这个模块在 `local.docs/产品功能规划.md` 里已有对应的现状盘点条目，可以先读那部分作为线索、
快速定位到该看哪些文件，但不要只依赖它——那份文档可能滞后于代码，最终依据以你自己读到的代码为准。
如果没有对应条目（新模块，或盘点文档已过期），直接自己扫描代码分析，不需要用户先去更新盘点文档。

### 第 3 步：识别需要产品判断的点，主动向用户确认

这是最容易漏做、但对"减少人工返工"最关键的一步。边写边留意三类信号：

- 草稿里写了"本期不考虑""某规则待定"这类明确留白的地方；
- 代码里能看到多种可能的行为，但看不出"哪种才是产品真正想要的"（例如某个字段代码没做校验，
  可能是"本期就是不需要校验"，也可能是"漏做了，正式产品需要校验"——这个判断代码本身回答不了）；
- 需要教育行业/本产品业务经验才能拍板的规则（例如"截止时间该不该是必填项""评审页右侧该展示学生原始作答
  还是参考答题卡样式"），这类问题草稿和代码都不会给出答案，纯粹是产品决策。

遇到这类点，**使用当前环境可用的提问工具或直接在对话中向用户确认**，给出 2-3 个具体选项（不要只是"要不要做校验？"这种笼统提问，
要带上你的推荐判断和理由，让用户可以直接选而不是重新思考一遍背景）。不要把这些问题写进文档留白，
也不要凭自己猜测直接下结论——猜错了就是这次生成没有达到"可直接交付"的目的，人工还是要大改。

如果同一份 PRD 里有多个类似的待确认点，可以合并询问，按当前工具支持的数量分批。
关键产品决策需要等用户回答后再定稿；等待期间可以继续整理不依赖这些答案的内容。

### 第 4 步：按格式规范写正文

写作时严格参照 `references/format-spec.md` 里总结的终版格式规范（章节顺序、字段表写法、
"现状说明"一律不保留等规则）。这份规范是从两份已定稿的终版 PRD 反推出来的，不要凭自己的判断
另起一套格式——保持所有模块的 PRD 风格一致，是这些文档能被长期维护、被其他 PRD 交叉引用的前提。

写之前先问自己：这一段/这张表，终版案例里有没有类似的先例？有先例就照着写法模式走，
没有先例（比如全新类型的模块）就按 format-spec.md 里"语言与排版细节"一节的通用原则处理。

版本记录里的"修改人"必须是真实姓名——生成前问用户这次挂谁的名字（默认沿用同一批 PRD 里
最近一次使用的姓名，除非用户说换人）。

### 第 5 步：写入文件并回顾

写入用户指定路径或目标项目的 `local.docs/AI PRD/PRD {模块名}.md`（模块名与草稿标题一致的简称，不带"（教师端）"这类后缀，
除非该模块确实有同名的学生端版本需要区分）。

写完后，简要说明输出文件位置和已确认的关键产品决策，不需要重新通读全文。
检查草稿范围是否全部覆盖、字段与状态是否一致、相关 PRD 的引用是否准确，以及格式是否符合规范。
如果仍有影响范围、字段或流程的决策未确认，不要遗漏后宣称终版；说明阻塞点并继续向用户确认。

## 参考文件

  写正文前务必看这份文件，不要凭记忆或直觉套用格式。
